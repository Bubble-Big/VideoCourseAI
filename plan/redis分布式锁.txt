设计 Redisson + WatchDog 分布式锁，基于 MD5 内容身份化实现内容级去重，解决「分片合并」与「AI 分析（ASR 转写 + DeepSeek 总结）」等长耗时任务带来的锁过期与重复消费问题。在测试并发场景下成功拦截重复提交，有效避免算力浪费，节省不必要的 AI Token 开销。

背景痛点
1. AI 分析链路非常昂贵：先要把音频抽出来，再跑 ASR 语音转文字，最后把全文喂给大模型做总结。整条链路 CPU 密集、耗时且长。
2. 接入的大模型 API 是按 Token 计费的，每一次调用都是真金白银。
在这种场景下处理任务时，我们不能容忍重复消费，但前端卡顿可能导致用户狂点「开始分析」按钮，瞬间发起 N 个相同的请求；换一个账号重复上传同一份视频，也会引发重复分析。
核心痛点：我们不能容忍同一个视频在同一时间被处理两次，这不仅是逻辑错误，更是烧钱和炸服务器。

选型问题
Q1: 为什么不采取本地 JVM 锁？
1. AI 分析与分片合并都是长耗时高资源消耗的场景，未来并发量上去是一定要扩容的。如果在单机阶段写死了 JVM 级别的原生并发锁，未来扩容时这些锁在跨服务器环境下就会彻底失效，核心业务的并发控制逻辑还得推翻重写。而用分布式锁，未来无论横向增加多少台服务器，核心代码一行都不需要修改，各个节点连接同一个 Redis 就能实现全局的并发调度。
2. 此外还有个务实的考量：系统本身已经为了分片上传的状态记录以及令牌桶限流引入了 Redis。既然 Redis 已经是当前架构的必选基础设施，直接复用它来实现分布式锁没有任何额外的运维和部署成本，技术栈更加收敛。

Q2: 为什么不采取 Redis set nx 锁？
SETNX 虽然简单，但在本项目的长耗时场景下有两个致命缺陷，所以必须用 Redisson：
1. 无法解决「锁过期」问题：如果用 SETNX，必须设置一个过期时间。但分片合并或 AI 分析可能要几分钟。如果时间到达后锁过期了，任务还没跑完，第二个线程就会加锁成功，导致并发冲突。Redisson 的 WatchDog 机制可以优雅地解决这个问题，它会自动续期。

项目中的三把分布式锁
实际的锁不止一把，按「锁的粒度」分为两类、三把：

| 锁 Key | 粒度 | 用途 | 抢锁方式 |
| --- | --- | --- | --- |
| lock:merge:{uploadId} | uploadId 维度 | 防止同一个上传任务被重复合并 | tryLock()（看门狗续期） |
| lock:analysis:{contentHash} | 内容（MD5）维度 | 同一内容只跑一次完整分析（跨 mediaId 串行） | tryLock()（看门狗续期） |
| lock:analysis-context:{contentHash} | 内容（MD5）维度 | 同一内容只做一次 ASR 转写 | 分析链路 tryLock(300s) 等待；独立转写 tryLock() 不等 |

说明：
- 分片合并锁按 uploadId 标识，解决的是「同一次上传被并发触发多次合并」的问题，与内容无关。
- 分析锁与转写锁都按 contentHash（内容 MD5）标识，解决的是「同一份视频内容被重复分析 / 重复转写」的问题，能做到跨 mediaId、跨用户的串行化与复用。
- 锁的 Key 统一集中在 AnalysisTaskKeys 工具类中维护，避免散落各处拼错前缀。

Redisson 设计和实现流程
Q1: 加锁的身份（Key）是怎么选的？
锁的身份不是简单的数据库自增 id，而是「内容指纹（contentHash）」。视频的「身份」= 内容 MD5。这样做的好处是，不仅能防止同一个任务重复提交，还能实现内容级别的去重——如果两个用户上传了同一个视频（换 mediaId 重复上传），系统也能识别出来，避免重复转码浪费算力。

不过 contentHash 并不是直接把 fileMd5 拿来当 Key，而是经过一层标准化（见「MD5 内容身份化设计」）：
- 合法的 32 位 MD5 统一转小写返回；
- 非法（历史数据 / 直传改造前上传没有算 MD5）则回退为 media-{id}，保证锁 Key 仍然唯一、不会因空 MD5 导致所有任务挤在同一把锁上。

Q2: 加锁争抢（tryLock）怎么做的？
分两条链路，语义不同：
- 提交侧（DebugController /ai 接口）：不用分布式锁，而是用幂等键 analysis:active:{contentHash} 做 setIfAbsent 原子抢占。抢不到直接返回 409「任务提交中，请勿重复提交」，把重复请求在入口处就挡掉，不进入 MQ。
- 消费侧（VideoAnalysisConsumer 消费 MQ 消息时）：调用 Redisson 的 tryLock() 获取内容级分析锁 lock:analysis:{contentHash}。如果获取失败，说明该内容正在被其他线程处理，直接静默 ACK 跳过这条重复消息（而非提示用户，因为这时请求已经投递到 MQ 了）。

Q3: 长任务续期（WatchDog）？
因为分片合并、AI 分析都非常耗时，很难预估过期时间。所以在加锁时没有设置过期时间（leaseTime = -1）。这时候 Redisson 会自动启动 WatchDog（看门狗）机制：
- WatchDog 本质就是后台的一个定时任务。默认每隔 10s 检查一下，如果任务还未完成，就自动把锁的过期时间重置为 30 秒。
- 这可以完美解决「业务没跑完，锁先过期导致并发冲突」的难题，也是为什么不采取 Redis set nx 锁。

Q4: 安全释放？
业务执行成功或者抛出异常，都会在 finally 里先判断 isHeldByCurrentThread() 再调用 unlock() 释放锁。Redisson 内部有防死锁机制：如果服务器宕机，WatchDog 线程挂掉，不再续期，锁会在 30 秒后自动过期，不会造成死锁。

MD5 内容身份化设计
MD5（Message-Digest Algorithm 5）是一种密码散列函数。在本项目中，利用它将任意长度的视频文件数据计算出一个 32 位的哈希值，作为内容的「数字指纹」：只要文件内容有一比特差异，生成的 MD5 值就完全不同。

1. contentHash 标准化
normalizeContentHash(mediaId, md5)：
- md5 合法（32 位十六进制）→ 统一转小写返回；
- 非法（历史数据 / 改造前上传）→ 回退为 media-{id}。
这是对 MD5 埋的「钩子」：既保证内容级去重，又对脏数据有兜底。

2. contentHash 的统一获取（MediaService.contentHash）
三级取值：先查 Redis 缓存 media:md5:{mediaId}（7 天 TTL）→ 未命中则查 DB 的 fileMd5 → 再标准化返回，并回写缓存。这样锁、幂等、复用三处拿到的都是同一份内容身份。

3. Redis Key 集中管理（AnalysisTaskKeys）
锁与复用相关的 Key 全部收敛在一个工具类里：
- 分析锁 lock:analysis:{contentHash}
- 转写锁 lock:analysis-context:{contentHash}
- 转写归属 analysis:context-owner:{contentHash}（记录哪个 mediaId 已产出转写文本，7 天 TTL）
- 分析结果归属 analysis:completed-owner:{contentHash}（记录哪个 mediaId 已产出完整分析，7 天 TTL）
- 提交侧幂等键 analysis:active:{contentHash}（30s TTL）

4. 归属复用（内容级去重的核心补充）
锁解决的是「并发同时处理」，归属复用解决的是「先后处理同一内容」：
- 转写归属：拿到转写锁后先查 analysis:context-owner，若已有别人转写过，直接复制文本，不再跑 ASR。
- 结果归属：分析开始时先查 analysis:completed-owner，若同一内容已有成功分析，直接复制 summary，不再烧 ASR + LLM。
归属都带 7 天 TTL，且在归属指向的记录失效（如转写失败）时会清掉归属，避免误复用。归属缓存过期或 Redis 重启丢失后，会回退 MySQL 按 file_md5 反查一条已 SUCCESS 的记录继续复用（依赖 file_md5 上的普通索引 idx_file_md5），查到后回填 Redis 归属。因此内容级复用本质是持久的，Redis 归属只是加速缓存，不再是唯一权威。

5. 关于 MD5 哈希碰撞
MD5 存在极小概率的碰撞。理论上可以用 MD5+时间戳降低碰撞概率，但那样就无法做到内容级去重（同一内容每次算出的指纹不同）。本项目优先保证内容级去重，因此 fileMd5 就是纯 MD5，不加时间戳。

WatchDog 机制
WatchDog 的原理其实是一个后台定时任务。
续期机制：当加锁成功且没有指定过期时间时，Redisson 会默认设置锁的超时时间为 30 秒（LockWatchdogTimeout）。WatchDog 会启动一个后台线程，每隔 10 秒（也就是 1/3 的超时时间）去轮询试探一下是否持有锁，如果还在，就重置过期时间为 30 秒。这样只要业务还在跑，锁就永远不过期。
宕机死锁问题（关键防御）：绝对不会死锁。这个后台定时任务和业务线程所在的 JVM 是死死绑定的。如果服务器宕机 / 断电了，WatchDog 线程也就挂了，自然就不会再续期。Redis 里的锁等到 30 秒倒计时一结束，就会自动过期释放，其他节点就可以正常拿到锁了。

Redisson 底层是怎么保证原子性
Redisson 底层是利用 Redis 的 Lua 脚本来保证原子性的。
Redisson 并没有分开发送命令，而是把「判断锁是否存在」「设置 Hash 值」「设置过期时间」这些逻辑都写在了一段 Lua 脚本里，然后把整个脚本发给 Redis 执行。因为 Redis 是单线程模型，当 Redis 执行一段 Lua 脚本时，它会把这个脚本看作一个整体，在脚本执行结束之前，Redis 绝对不会去执行其他客户端发来的命令。
无论并发有多高，在 Redis 看来，所有的抢锁请求都是排好队、一个接一个执行 Lua 脚本的。这就从底层物理上保证了操作的原子性，彻底杜绝了并发冲突。

内容级去重的前置兜底保障
Q1: 内容级去重在锁外还有别的保障机制吗？
本项目的内容级去重是「分层防御」，按「何时拦截」分三层，每一层堵住一类重复：

1. 第一层：提交侧幂等键 + 状态校验（拦截「同时刻狂点」）。
用户在控制台点击「AI 分析」时，请求先按 contentHash 去抢幂等键 analysis:active:{contentHash}（setIfAbsent，30s TTL）。抢不到说明同一内容正在提交 / 分析，直接 409 拒绝。抢到后还要查 aiStatus，若已处于 PENDING / PROCESSING 也直接 409。这一步在入口处就斩断了绝大多数「狂点按钮」带来的重复提交。

2. 第二层：消费侧内容级分布式锁（拦截「并发重复消费」）。
消息进入 RocketMQ 消费侧后，还要按 contentHash 抢 lock:analysis:{contentHash}。即便有重复消息或换 mediaId 重复上传，抢不到锁的消费线程直接静默 ACK 跳过，保证同一内容同一时间只有一个线程真正执行 ASR + LLM。

3. 第三层：归属复用（拦截「先后重复处理同一内容」）。
即使先后（非同时）处理同一内容，也会先查归属、命中已完成记录就直接复制结果，不再重新烧算力。这一层又分两段，构成「缓存 + 持久」的完整兜底：
- Redis 归属缓存：analysis:completed-owner / analysis:context-owner（7 天 TTL），命中直接复用，是最快的路径。
- MySQL 反查兜底：归属缓存过期或 Redis 重启丢失后，回退按 file_md5 反查一条已 SUCCESS 的记录（依赖普通索引 idx_file_md5）继续复用，查到后回填 Redis 归属。
正是有了 MySQL 反查兜底，内容级复用才从「7 天易失缓存」升级为「与数据库同生命周期的持久能力」，Redis 归属退化为纯加速缓存。这一层把「历史同源视频被二次重复处理」的可能也彻底堵住了。

Q2: 为什么不全靠 MySQL 来去重，还要费劲引入 Redisson？
核心原因在于关系型数据库根本扛不住瞬时并发洪峰。面对前端异常或恶意脚本瞬间涌入的大量重复请求，如果完全依赖 MySQL 的查询去硬抗并发冲突，海量的无效查询会迅速耗尽数据库连接池，拉高系统全局的响应延迟甚至导致整个服务宕机。
Redis 作为纯内存组件，其核心架构使命就是挡在脆弱的关系型数据库前面吸收并发火力。我们用幂等键 + Redisson 分布式锁把瞬时并发的无效请求全部拦截在内存层，只放行唯一一个合法线程去执行极其昂贵的 AI 算力调用，最后才与 MySQL 交互落盘。
这套架构的职责分工是互补的：Redis 负责抗高并发冲突（幂等键 / 分布式锁 / 归属缓存，快但易失），MySQL 负责持久兜底（历史结果存储 + file_md5 反查复用，慢但持久）。Redis 挡住瞬时洪峰，MySQL 保证长期去重——既不牺牲并发性能，也不依赖易失缓存。

（说明：本项目并未在 MySQL 的 file_md5 字段上建立唯一约束，也没有依赖 DuplicateKeyException 做物理兜底——因为同一内容允许跨用户各留一条记录，file_md5 天然可重复。file_md5 上建的是普通索引 idx_file_md5，作用是为「按内容反查已完成记录」加速，而非强制存储层唯一。）
