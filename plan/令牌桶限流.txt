基于 Redis（Redisson RRateLimiter）实现令牌桶限流，按「用户级 + 全局级」双层设置每分钟请求上限，遏制恶意请求带来的高昂 API 调用成本，保障服务可用性。

技术选型
(对比 cityhub 选型)
因为只有令牌桶算法能同时满足「限制平均速率」和「允许突发流量」这两个核心需求，用户体验最好。
1. 对比固定窗口（Fixed Window）：解决「临界突发」风险。固定窗口太死板。如果我限制每分钟 60 次，可能会出现「第 0.9 分钟来了 60 次，第 1.1 分钟又来了 60 次」的情况。虽然每分钟都没超标，但在极短时间内瞬间涌入 120 次请求，容易把服务打挂。令牌桶是基于流速的，平滑地解决了这个问题。
2. 对比漏桶（Leaky Bucket）：解决「响应迟钝」问题。漏桶强制请求像滴水一样匀速通过。如果现在服务器很空闲，突然来了一波正常请求，漏桶也会强行让它们排队，导致用户响应变慢。而令牌桶允许「攒令牌」。如果有库存，突发流量可以瞬间拿走令牌立即执行，不需要无意义的排队，这对互联网业务的用户体验至关重要。

具体流程
本项目没有重复造轮子自己写 Lua 脚本 + Hash 结构，而是直接使用 Redisson 内置的令牌桶组件 RRateLimiter 实现，原子性由 Redisson 内部保证。

1. 双层限流（用户级 + 全局级）
限流与「内容」无关，key 固定为用户维度 / 全局维度：
- 用户级：limit:ai:user:{userId}（AI 分析）/ limit:transcribe:user:{userId}（文字提取）
- 全局级：limit:ai:global / limit:transcribe:global

2. 配额（每分钟）
- AI 分析（transcribe + summary 一次完整分析）：用户级 5 次/分 + 全局级 30 次/分
- 纯文字提取（仅 ASR，成本低于完整分析）：用户级 10 次/分 + 全局级 60 次/分

3. 执行流程（RRateLimiter）
当请求进来时，先对用户级限流器调用 trySetRate 初始化速率（RateType.OVERALL，每分钟 rate 个令牌），再 tryAcquire 尝试拿一个令牌；用户级通过后再对全局级做同样操作。两层都通过才算准入。
- tryAcquire 返回 false → 抛出 BusinessException(RATE_LIMITED)，对应 HTTP 429，表示真超限。
- 若 Redis 限流器本身不可用（连不上 / 异常）→ 抛出 BusinessException(SERVICE_UNAVAILABLE)，对应 HTTP 503，避免把基础设施故障误报成「请求太频繁」。

细节问题
Q1: 令牌桶的原子性是怎么保证的？
必须保证原子性，不用会有严重的并发漏洞。令牌桶的逻辑本质是一个「先检查后执行」的复合操作：先读桶里还剩多少令牌，判断够不够，再扣减。如果这三个步骤分多次网络请求在 Java 端执行，高并发下极可能出现两个线程同时读到还剩 1 个令牌、都认为自己抢到了，分别扣减导致令牌数变负，限流阈值就被击穿了。
Redisson 的 RRateLimiter 底层正是用 Redis 的 Lua 脚本把这套「读、算、写」逻辑打包成一条命令原子执行：Redis 单线程执行 Lua 脚本时绝不会被其他命令插队，从而严格保证了计数器的准确性。这也正是上一份文档里 Redisson 分布式锁保证原子性的同一套机制。

Q2: 请求被限流了，前端怎么处理
被限流的请求，后端返回 HTTP 429 状态码和「请求过于频繁，请稍后再试」的提示。同时区分了两种失败语义：真超限返回 429（RATE_LIMITED）；Redis 限流器本身不可用返回 503（SERVICE_UNAVAILABLE）。前端收到 429 后会展示友好提示，引导用户稍后重试；收到 503 则提示「服务暂不可用」，避免误导用户。

设计 阶梯式延迟重试机制 应对三方 API 网络抖动，结合最终一致性保障，任务成功率极大提升。
背景痛点
调用第三方大模型 API 时常遇到网络波动或接口限流。直接失败对用户的体验很不好，我们宁愿多等几秒尝试增加任务成功的几率，就此引出了重试机制解决这个痛点。

Q1: 为什么采取阶梯式延迟重试而不是其他的时间梯度？
1. 立即重试：报错的瞬间立刻再发请求。如果网络正在抖动，立刻发大概率还是报错，纯属白费力气。
2. 固定间隔重试：强制约定每隔两秒重试一次。一旦第三方 API 大面积宕机，系统里所有失败的任务都会每隔两秒准时发起一波集体冲锋。这极易引发羊群效应，直接把对方服务器彻底打死，或者触发对方的风控安全机制，导致 IP 被拉黑。
3. 阶梯式延迟重试：等待时间逐级拉长，本质上就是给对方服务器留出喘息恢复的时间。对方故障越久，系统退避等待的时间就越长。这既不空耗线程算力，也避免了把下游第三方服务逼上绝路。

实现流程
本项目没有重复造轮子，而是基于 RocketMQ 消费者原生的重试策略来实现的，它天然就支持阶梯式的时间等待。
1. 同步消费 + 异常上抛：消费侧 VideoAnalysisConsumer 采用同步消费（不再 runAsync 立即 ACK 吞异常），业务异常在 onMessage 内上抛，交给 RocketMQ 触发重投。
2. 异常分层（AiAnalysisException(retryable)）：
   - 永久失败（retryable=false，如文件不存在、转写永久失败）→ 写失败台账 failed_analysis_task，然后正常 ACK，不再重投。
   - 瞬时失败（retryable=true，如网络抖动、API 超时）→ 同样写台账记录本次失败，再上抛异常触发重投。
3. 阶梯延迟：RocketMQ 按默认延迟级别重投，第一次重投等约 10s，之后 30s、1m…… 时间逐级拉长，有效防止下游服务雪崩。
4. 最终一致性：不能无限重试。消费监听器上设置了 maxReconsumeTimes = 2（2 次重投 = 最多 3 次投递）。投递耗尽后消息进入 RocketMQ 默认的死信队列（%DLQ%），同时失败过程全程有 failed_analysis_task 台账可查，保障数据可追溯。

兜底策略
Q1: 你怎么去解决幂等性？
重试了多次，万一第一次其实调用成功了，只是因为网络超时没收到响应，重试会不会导致重复分析、重复扣费？
本项目的幂等不依赖「数据库唯一索引」，而是靠「MD5 内容身份化」在 Redis 层兜底（详见 redis分布式锁.txt）：
- 提交侧用内容级幂等键 analysis:active:{contentHash} 做 setIfAbsent 抢占，同一内容重复提交直接 409 拒绝；
- 消费侧用内容级分布式锁 lock:analysis:{contentHash} 保证同一内容同一时间只有一个线程真正执行；
- 结果归属复用 analysis:completed-owner:{contentHash} / 转写归属 analysis:context-owner:{contentHash} 保证先后处理同一内容时直接复制结果、不再重复烧算力。
即便 MQ 因为网络超时重投同一条消息，消费侧也会被分布式锁拦下（重复投递直接静默 ACK 跳过），或在锁内命中已完成结果直接复用返回。这样利用「内容指纹 + 分布式锁 + 归属复用」的组合，确保了同一内容绝不会被重复分析、重复计费。

Q2: 重试耗尽了还是失败怎么办
本项目不追求无限重试。投递次数由 maxReconsumeTimes = 2 封顶，耗尽后消息进入 RocketMQ 默认死信队列（%DLQ%）。同时每次失败（无论永久还是瞬时）都会写入失败台账 failed_analysis_task（记录 media_id、error_type、error_msg、attempts），前端状态字段也会落为 FAILED。这样即使消息进了 %DLQ%，也可以通过台账和状态字段定位到具体失败记录，便于后续排查与人工介入。
